## Неблокирующие read и write. Развитие сервера с тред пулом: busy loop polling. Проблемы такой реализации.

### Эволюция сервера: откуда взялся проблема

К этому моменту у нас есть многопоточный сервер с тред-пулом: пул из N потоков, очередь задач, 
каждый клиент обслуживается одним потоком. Но потоки блокируются на `read()` — пока клиент не прислал данные, поток спит. 
При 10 000 клиентов нужно 10 000 потоков. Это не масштабируется.

Решение — сделать I/O неблокирующим, чтобы один поток мог опрашивать много дескрипторов.

### Неблокирующий режим: `O_NONBLOCK`

Флаг `O_NONBLOCK` переводит файловый дескриптор в режим, где системные вызовы никогда не блокируют поток:

```cpp
#include <fcntl.h>

// Установить неблокирующий режим на существующий fd
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

// Или сразу при accept (Linux 2.6.28+)
int client_fd = accept4(server_fd, nullptr, nullptr, SOCK_NONBLOCK);
```

### Неблокирующий `read()`

```cpp
ssize_t n = read(fd, buf, sizeof(buf));

if (n > 0) {
    // Данные получены — обрабатываем
} else if (n == 0) {
    // EOF — клиент закрыл соединение
} else {
    // n == -1, смотрим на errno:
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        // Данных нет прямо сейчас — попробуем позже
        // Это НЕ ошибка!
    } else {
        // Реальная ошибка
    }
}
```

### Неблокирующий `write()`

```cpp
ssize_t n = write(fd, buf, len);

if (n > 0) {
    // Записано n байт (может быть меньше len — partial write!)
} else if (n == -1) {
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        // Буфер отправки ядра полон — нужно подождать
        // Данные ещё НЕ отправлены!
    }
}
```

Важно: при `write()` в неблокирующем режиме может записаться меньше байт, чем просили — это нормально, нужно отправлять остаток позже.

### Busy Loop Polling: идея

Теперь у нас есть неблокирующий I/O. Как опрашивать множество клиентов? Первая идея — крутить цикл по всем соединениям и проверять каждый:

```cpp
std::vector<int> clients; // все активные fd

void worker_thread() {
    while (true) {
        for (int fd : clients) {
            char buf[4096];
            ssize_t n = read(fd, buf, sizeof(buf));

            if (n > 0) {
                process(fd, buf, n);       // есть данные — обработать
            } else if (n == 0) {
                close_connection(fd);      // клиент ушёл
            } else if (errno == EAGAIN) {
                continue;                  // нет данных — идём дальше
            }
        }
        // Прошли всех — начинаем снова
    }
}
```

Каждый поток в тред-пуле крутит этот цикл над своей порцией клиентов.

```text
Тред-пул из 4 потоков, 1000 клиентов:

Поток 1: fd[0..249]   → опрашивает непрерывно
Поток 2: fd[250..499] → опрашивает непрерывно
Поток 3: fd[500..749] → опрашивает непрерывно
Поток 4: fd[750..999] → опрашивает непрерывно
```

### Проблемы busy loop polling

1. Сжигание CPU впустую

Главная проблема: если большинство клиентов молчат (а так обычно и бывает), поток делает тысячи холостых `read()` → `EAGAIN` в секунду:

```text
Поток:  read(fd0)→EAGAIN, read(fd1)→EAGAIN, ..., read(fd249)→EAGAIN
        read(fd0)→EAGAIN, read(fd1)→EAGAIN, ...   ← снова и снова
        CPU: 100% 🔥 — хотя реальной работы 0
```

При 4 потоках — 4 ядра загружены на 100% без какой-либо полезной нагрузки.

2. Latency vs CPU tradeoff

Единственный способ снизить нагрузку — добавить sleep() между итерациями:

```cpp
for (int fd : clients) { ... }
std::this_thread::sleep_for(std::chrono::milliseconds(1)); // костыль
```

Но это создаёт задержку обработки: данные, пришедшие сразу после начала sleep, будут ждать до 1ms. Получается дилемма:

```text
Маленький sleep → мало задержки, но CPU всё равно горит
Большой sleep  → низкая нагрузка, но высокая задержка
Нет sleep      → нулевая задержка, но 100% CPU
```

Нет значения sleep, которое было бы хорошим в обоих измерениях.

3. Масштабирование по числу клиентов

Время одного прохода цикла растёт линейно с числом клиентов: при 10 000 клиентов один проход занимает заметное время, даже если все отвечают `EAGAIN`:

```text
1 000  клиентов → 1 000  syscall за проход
10 000 клиентов → 10 000 syscall за проход  ← O(N) даже при 0 активных
```

Syscall — дорогая операция (переключение в режим ядра). 10 000 пустых `read()` — огромные накладные расходы.

4. Неэффективное использование тред-пула

Потоки никогда не спят — они не освобождают CPU для других задач ОС. Планировщик не может их вытеснить полезным образом, потому что они формально «работают».

5. Проблема частичной записи

При неблокирующем `write()` нужно отслеживать, сколько байт записалось, и хранить буфер с остатком для каждого клиента:

```cpp
// Надо хранить для каждого fd:
struct ClientState {
    std::vector<char> write_buf;  // что ещё не записано
    size_t write_offset;          // с какого места
};
```
